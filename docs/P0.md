# P0 — 기술 검증 (PoC) 가이드

설계(`docs/DESIGN.md`)에서 불확실했던 부분들을 실제 기기로 확인하는 단계다.
결과에 따라 P1(MVP)의 Android 주입 방식과 Android 호스트 범위가 정해진다.

| # | 검증 항목 | 코드 | 통과 기준 |
|---|---|---|---|
| P0-1 | Windows 전역 키보드·마우스 캡처 + 로컬 차단 | `poc/win-capture` | 원격 모드에서 로컬이 아무 입력도 받지 않고, 모드 전환 시 키가 눌린 채로 남지 않음 |
| P0-2 | Android 특권 주입 (Shizuku) — UHID / Inject | `android/` (주입 방식 1·2) | 포인터 표시, 클릭·드래그·휠, 영문·단축키·한글 입력 |
| P0-3 | Android 접근성 + IME 주입 | `android/` (주입 방식 3) | 탭·스크롤·뒤로가기, IME 선택 시 영문 입력 |
| P0-4 | Android evdev 읽기 + 독점(grab) | `android/` "evdev 프로브" | 외부 키보드/마우스 이벤트가 읽히고, grab 중 화면이 반응하지 않음 |
| P0-5 | Android 호스트 → 블루투스 키보드·마우스 | `android/` 호스트 시작 · "블루투스 중계" | Windows가 앱 없이 폰을 블루투스 키보드·마우스로 인식, 단축키로 폰↔PC 전환 |

> ⚠️ P0 프로토콜은 **암호화·인증이 없다** (P1에서 Noise로 교체). 신뢰할 수 있는 집 네트워크에서만 실행할 것.
> Android 리시버는 같은 서브넷이 아닌 주소의 연결을 거부한다.

## 1. 구성물

```
core/proto        PoC 와이어 포맷 v0 (u16 길이 | u8 타입 | 페이로드, big endian)
core/keymap       USB HID usage ↔ Windows 스캔코드 / Linux evdev 변환표
poc/kmc           테스트 도구 (Windows/Linux/macOS)
                    kmc dump             : 받은 이벤트를 출력하는 가짜 리시버
                    kmc demo <ip>        : 마우스 이동·클릭·스크롤·타이핑 스크립트 전송
                    kmc ping <ip>        : 왕복 지연 측정
poc/win-capture   P0-1 Windows 호스트 (LL 훅 + Raw Input)
android/          P0-2/3/4 Android 앱 (리시버 + evdev 프로브)
```

## 2. 빌드

### GitHub Actions 산출물 (권장)
브랜치에 push하면 CI가 빌드한다. Actions 실행 결과 페이지의 **Artifacts**에서 받는다.
- `keymanc-p0-windows` → `win-capture.exe`, `kmc.exe`
- `keymanc-p0-apk` → `app-debug.apk`

### 로컬 빌드
```sh
# Windows (Rust 설치 필요)
cargo build --release -p win-capture -p kmc

# Android (JDK 17 + Android SDK, 또는 Android Studio로 android/ 열기)
cd android && ./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

## 3. 준비: Android

1. APK 설치 후 앱 실행 → 알림 권한 허용.
2. **Shizuku** (P0-2, P0-4): Play 스토어/GitHub에서 Shizuku 설치 → "무선 디버깅으로 시작" 안내대로 페어링·시작
   → keymanc 앱에서 **Shizuku 권한** 버튼 → 허용.
3. **Inject 방식**을 시험할 때만: **오버레이 권한** 버튼 → "다른 앱 위에 표시" 허용 (커서 그리기용).
4. **접근성 방식** (P0-3): **접근성 설정** → 설치된 앱 → keymanc 켜기.
   키 입력까지 보려면 **키보드 설정**에서 keymanc 사용 설정 → **키보드 선택**으로 keymanc 선택.
5. 화면 상단의 IP 주소를 메모한다.

PC 없이도 **자체 테스트** 버튼으로 네트워크를 거친 전체 경로(루프백)를 확인할 수 있다.
테스트 칸에 `keymanc 123` 이 입력되고, 한/영 전환이 된다면 `한글`도 입력되어야 한다.

## 4. 검증 절차

### P0-1 Windows 캡처

```powershell
# 1) 네트워크 없이: 무엇이 전송될지 출력만
win-capture.exe --dry-run

# 2) 가짜 리시버로: 다른 PC(또는 같은 PC의 다른 창)에서
kmc.exe dump
win-capture.exe 127.0.0.1         # 같은 PC면 127.0.0.1

# 3) Android로: 앱에서 리시버 시작 후
win-capture.exe 192.168.x.y
```

단축키: `Ctrl+Alt+→` 원격, `Ctrl+Alt+←` 로컬, `Ctrl+Alt+Shift+Esc` 비상 복귀. 창을 닫으면 훅도 해제된다.

확인할 것:
- [ ] 원격 모드에서 로컬 커서가 움직이지 않고, 키 입력이 로컬 창에 들어가지 않는다
- [ ] `Ctrl+Alt+→` 후 Ctrl/Alt를 떼도 로컬에서 Ctrl/Alt가 눌린 채 남지 않는다 (예: 메모장에서 글자 입력 정상)
- [ ] 원격에서 Shift를 누른 채 `Ctrl+Alt+←` 로 돌아와도 원격·로컬 모두 Shift가 남지 않는다
- [ ] 한/영 키(또는 오른쪽 Alt)가 `Lang1(Hangul)` 로 전송된다 (`--dry-run` 출력 확인)
- [ ] 마우스 이동이 부드럽고 (`[net] rtt` 로그의 p50/max 기록), 휠·좌/우/가운데·앞/뒤 버튼 전달
- [ ] 관리자 권한 창(작업 관리자 등)이 포커스일 때의 동작 기록 — 일반 권한/관리자 권한 실행 각각
- [ ] 게임 등 Raw Input을 쓰는 앱이 원격 모드 중 마우스를 받는지 기록 (LL 훅으로는 Raw Input을 막지 못할 수 있음)

### P0-2 Android 특권 주입 (UHID → Inject 순서로)

앱에서 주입 방식을 고르고 **시작** → PC에서 `kmc demo <폰 IP>` 또는 `win-capture <폰 IP>`.
주입 방식을 바꾸면 **중지 → 시작**해야 적용된다.

확인할 것 (방식별로):
- [ ] 리시버 시작 성공 (로그에 `UHID keyboard + mouse created` 또는 `privileged: uid=2000 … inject=ok`)
- [ ] 마우스 포인터가 보이고 따라온다 (UHID: 시스템 포인터 / Inject: 앱이 그린 화살표)
- [ ] 클릭, 드래그(아이콘 이동·텍스트 선택), 휠 스크롤, 우클릭, 앞/뒤 버튼
- [ ] 영문 타이핑, `Ctrl+A/C/V`, 방향키, Backspace, 키를 누르고 있을 때 반복
- [ ] 한/영 전환: 설정 3가지(Shift+Space / Ctrl+Space / 그대로) 중 어느 것이 이 기기 키보드 앱에서 동작하는지
- [ ] 다른 앱(홈 화면, 브라우저) 위에서도 동작 = 백그라운드 동작
- [ ] 화면을 껐다 켠 뒤, Wi-Fi 재연결 뒤 재접속
- [ ] 로그의 `sink: N events, avg … µs` 값 기록, 체감 지연(PC 커서와 비교)

### P0-3 Android 접근성 + IME

주입 방식 3을 고르고 P0-2와 같은 절차.
- [ ] 오버레이 커서 표시·이동
- [ ] 탭(클릭), 길게 누르기(버튼을 0.5초 이상 누름), 드래그(놓을 때 한 번에 재생됨)
- [ ] 휠 → 스크롤, 우클릭 → 뒤로가기, 가운데 → 최근 앱
- [ ] keymanc IME 선택 시 영문·Ctrl 단축키 입력 / 미선택 시 Esc→뒤로, Win→홈만 동작
- [ ] 체감 품질을 특권 모드와 비교

### P0-4 Android evdev (호스트 가능성)

Android에 USB OTG 또는 블루투스 키보드·마우스를 연결 → **evdev 열기/grab 테스트 (10초)** → 10초 동안 사용.
- [ ] 로그에 장치 목록과 `open ok, grab ok` 가 나오는가
- [ ] 결과에 해당 장치의 `events=` 가 0보다 큰가
- [ ] grab 중(10초 동안) 화면이 그 키보드·마우스에 **반응하지 않았는가**

### P0-5 Android 호스트 → 블루투스

준비: 앱의 **블루투스 권한** 버튼 → 허용, 폰 블루투스 켜기.
입력 캡처는 Shizuku가 있으면 Shizuku, 없으면 **접근성 서비스**(설정 → 접근성 → keymanc 켜기)를 쓴다.
로그의 `host capture: Shizuku …` / `host capture: accessibility …` 로 어느 쪽인지 확인할 수 있다.

블루투스 방식은 **BLE(기본)**. 클래식은 폰에 연결된 블루투스 키보드·마우스를 끊으므로 비교용으로만 쓴다.

**5-a. 블루투스 경로만 먼저 (키보드·마우스 없이)**
1. 주입 방식에서 **블루투스 중계**를 고르고 리시버 **시작** → 로그에 `BLE HID ready`
2. Windows `설정 → 블루투스 및 장치 → 장치 추가 → 블루투스` 에서 폰 이름 선택 (폰에 페어링 확인 창이 뜨면 허용)
   - 목록에 폰이 없으면:
     - Windows 11은 기본 검색 모드에서 "기타 장치"를 숨긴다. Android 앱은 광고에 기기 종류(Appearance)를
       넣을 수 없어 keymanc가 여기에 해당한다 → `설정 → 블루투스 및 장치 → 장치 → Bluetooth 장치 검색 = 고급`,
       또는 `제어판 → 장치 및 프린터 → 장치 추가`
     - 예전에 이 PC와 폰을 페어링했다면 양쪽에서 먼저 삭제 (Windows: 장치 제거 / 폰: 등록 해제)
     - 로그에 `BLE HID: advertising` 이 있는지 확인
   - 페어링하는 동안 폰의 블루투스 설정 화면은 닫아 둘 것 (열려 있으면 Windows가 클래식 "휴대폰"으로 페어링할 수 있음)
3. 로그에 `BLE HID: <PC 이름> ready` 와 `active target → <PC 이름>` 확인
4. PC에서 `kmc demo <폰 IP>` → **PC 화면**에서 커서가 움직이고 메모장에 글자가 입력되는지

**5-b. 실제 호스트**
1. 폰에 블루투스/USB 키보드·마우스 연결, 리시버는 **중지**
2. **호스트 시작** → 로그에 `captured eventN "<장치 이름>"` 과 `BT HID: connected`
3. 평소처럼 폰을 조작 (키보드·마우스가 폰에서 그대로 동작해야 함 = UHID 패스스루)
4. `Ctrl+Alt+→` → 키보드·마우스가 PC를 조작 / `Ctrl+Alt+←` → 다시 폰
5. (여러 대상) 두 번째 PC·태블릿도 같은 방법으로 추가 → 대상 조작 중 `Ctrl+Alt+→` 를 다시 누르면 다음 대상

확인할 것:
- [ ] Windows가 추가 앱 없이 키보드·마우스로 인식 (장치 관리자에 "HID 키보드/마우스")
- [ ] 이동·클릭·휠·드래그, 영문 타이핑, `Ctrl+C/V`, 키 반복
- [ ] 한/영 키가 Windows에서 한/영 전환 (Windows 키보드 종류가 "한국어 키보드(103/106키)"일 때)
- [ ] 로컬(폰) 조작이 캡처 전과 똑같은지, 폰의 키보드 배열 설정이 `keymanc Passthrough Keyboard` 에 적용되는지
- [ ] 전환 후 Ctrl/Alt/Shift가 양쪽 어디에도 눌린 채 남지 않음
- [ ] PC 블루투스를 끄면 자동으로 폰으로 복귀, 다시 켜면 재연결 (앱이 마지막 대상에 자동 연결)
- [ ] 호스트 중지 또는 앱 강제 종료 후 키보드·마우스가 폰에서 정상 동작 (grab 해제)
- [ ] 체감 지연 (블루투스)
- [ ] 호스트 실행 중에도 폰의 블루투스 키보드·마우스가 **연결됨** 유지 (BLE 모드)
- [ ] 대상 2개 이상에서 `Ctrl+Alt+→` 즉시 전환, 전환 후 이전 대상에 키가 남지 않음
- [ ] (접근성 방식) 키보드 전환·입력, Android 14+에서 마우스가 대상으로 가는지, 이때 폰의 클릭이 막히는지·폰 포인터가 움직이는지

## 6. 알려진 PoC 한계 (P1에서 해결)

- 암호화·페어링·mDNS 탐색 없음 — IP 직접 입력, 고정 포트 45877
- Windows 호스트는 리시버 1대, 단축키 고정, 트레이 UI 없음 (콘솔)
- 접근성 모드의 드래그는 실시간이 아니라 버튼을 놓을 때 재생, 한글 조합 없음
- Android 키코드 표는 Kotlin에 따로 있음 → P1에서 Rust `keymap` + FFI로 통합
  (evdev → HID 표는 `tools/gen_android_keymap.py` 로 Rust에서 생성, CI가 불일치 검사)
- 블루투스 호스트: 대상 1개, 미디어 키 패스스루 없음, 대상 전환 UI 없음
