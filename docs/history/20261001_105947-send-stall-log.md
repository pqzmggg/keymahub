# 전송 지연: 원인 로그, 확인 대기 단축, 재시도 스레드 분리

- 왜: 가끔 입력이 몇백 ms 밀리는 느낌. 코드상 가장 그럴듯한 원인은 전송 확인(`onNotificationSent`)을 하나 잃으면 창(3개)이 찬 채 `IN_FLIGHT_TIMEOUT_MS`(250ms)를 기다리는 것. 재시도 타이머가 메인(UI) 스레드에 있어 앱 화면이 바쁘면 늦어질 수도 있었음. 로그가 없어 어느 쪽인지 알 수 없었음.
- 어떻게:
  - 로그: 보낼 입력이 50ms 이상 기다렸으면 대기 시간과 원인("waiting for confirmations" / "Bluetooth stack busy")을, 확인을 잃어 그냥 보냈으면 그 사실을 남김. 지연이 느껴질 때 로그에 없으면 폰 밖(무선·호스트) 쪽.
  - 확인 대기 250ms → 60ms: 확인은 연결 이벤트 한두 번(11~50ms) 안에 옴. 늦은 확인이 와도 개수가 0 아래로 내려가지 않고, 스택이 꽉 차면 바쁨으로 돌아와 다시 시도하므로 안전.
  - 전송 재시도는 전용 스레드(`ble-send`)에서. 링크 붙기 타임아웃·서비스 갱신은 그대로 메인 스레드.
  - 한계: 실기기 측정 전. 호스트가 짧은 간격을 거절해 50ms 간격이면 정상 대기도 로그에 남을 수 있음(그것도 원인 정보).
